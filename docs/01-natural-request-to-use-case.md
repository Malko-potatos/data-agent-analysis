# 01. Natural Request To Use Case

사용자 발화는 대부분 불완전하다. "마케팅 데이터를 분석하고 싶어요"라는 말 안에는 목적, 데이터, 현재 방식, 위험, 반복성, 검증 기준이 섞여 있다.

첫 단계는 프롬프트 작성이 아니라 요구사항 해부다. 다만 비개발자가 처음부터 아래의 전체 표를 모두 채울 필요는 없다. 수업에서는 먼저 [쉬운 요청 카드](../templates/requirement-card.md)나 [DOCX 양식](../templates/data-analysis-agent-requirement-form.docx)의 앞쪽 질문만 채우고, 에이전트가 뒤에서 전문 항목을 보완하게 한다.

## Requirement Card

비개발자용 시작 질문은 다음 정도면 충분하다.

- 무엇을 알고 싶은가?
- 이 결과로 어떤 결정을 하고 싶은가?
- 데이터는 어디에 있는가?
- 지금은 어떻게 하고 있는가?
- 어떤 결과물이 있으면 좋은가?
- 꼭 조심해야 할 일은 무엇인가?
- 무엇과 비교하면 맞았다고 볼 수 있는가?

아래 표는 에이전트와 함께 보완하는 확장 카드다.

| 항목 | 질문 | 예시 |
|---|---|---|
| 사용자 | 누가 결과를 보는가? | 경영진, 재무 담당, 마케팅 담당, 운영자 |
| 목적 | 무엇을 알고 싶거나 개선하고 싶은가? | 매출 분석, 유입 개선, 진행률 관리 |
| 데이터 | 데이터는 어디 있는가? | DB, GA, 광고 플랫폼, 어드민, CSV, 커뮤니티 |
| 현재 방식 | 지금은 어떻게 처리하는가? | 어드민 다운로드, 수동 집계, Claude 분석 |
| 원하는 변화 | 무엇이 달라지길 원하는가? | 자동화, 대시보드, 리포트, 개선안 |
| 반복성 | 일회성인가 반복 업무인가? | 매일, 매주, 월간, 상시 모니터링 |
| 위험 | 무엇을 조심해야 하는가? | 민감정보, 잘못된 집계, 외부 발송, DB 변경 |
| 검증 | 무엇과 대조하면 맞았다고 볼 수 있는가? | 어드민 export, 기존 대시보드, DB total |

## How To Fill It

요구사항 카드는 완벽한 답을 요구하지 않는다. 모르면 "확인 필요"라고 남긴다. 중요한 것은 모르는 것을 추정으로 덮지 않는 것이다.

좋은 카드에는 세 가지가 분리되어 있다.

- 확인된 사실
- 합리적 추정
- 사람에게 물어봐야 하는 것

## Example

원 요구:

> 프로그램별 수업 진행상황이 자동 업데이트되어 대시보드로 보이면 좋겠습니다. 데이터는 DB에 있고 어드민에서 다운받아 분석하고 있습니다.

요구사항 카드:

| 항목 | 내용 |
|---|---|
| 사용자 | 운영자, 프로그램 매니저 |
| 목적 | 프로그램별 진행률과 지연 위험 파악 |
| 데이터 | DB, 기존 어드민 export |
| 현재 방식 | 어드민에서 다운로드 후 수동 분석 |
| 원하는 변화 | 자동 갱신 대시보드 |
| 반복성 | 상시 또는 매일 |
| 위험 | 프로그램별 완료 기준 차이, 중복 집계, DB 권한 |
| 검증 | 어드민 export와 DB 집계 비교 |

## Routing Hint

카드를 채운 뒤에는 다음 질문으로 use case를 좁힌다.

- 결과물이 분석 리포트인가, 반복 대시보드인가?
- 원천 데이터가 깨끗한가, 먼저 정제가 필요한가?
- 공식 metric이 있는가, 먼저 metric discovery가 필요한가?
- 외부 발송, 삭제, 배포, 권한 변경 같은 action이 있는가?
- 사람이 승인해야 하는 경계가 어디인가?
