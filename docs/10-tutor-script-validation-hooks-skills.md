# 10. Tutor Script: Verification, Hooks, Skills

이 문서는 튜터가 비개발자에게 "검증, hook, skill"을 설명할 때 그대로 읽거나 변형해 사용할 수 있는 대본이다.

## Opening

여러분, 오늘은 조금 헷갈릴 수 있는 단어를 쉽게 풀어보겠습니다.

우리가 방금까지 배운 것은 데이터 분석 요청을 자동화 가능한 업무 흐름으로 바꾸는 방법이었습니다. 그런데 자동화를 이야기하면 곧 이런 질문이 나옵니다.

> "그럼 검증은 어떻게 자동화하나요?"  
> "hook이나 skill은 비개발자가 직접 만들어야 하나요?"

정답부터 말하면, **비개발자가 hook이나 skill을 직접 만들 필요는 없습니다.**

비개발자가 해야 할 일은 코드를 짜는 것이 아니라, **매번 확인해야 하는 규칙을 말로 정리하는 것**입니다.

## Core Message

이렇게 기억하면 됩니다.

```text
비개발자는 검증 기준을 쓴다.
에이전트나 개발자는 그 기준을 checklist, prompt, skill, hook, automation으로 바꾼다.
```

비유해볼게요.

식당 사장님이 직접 주방 온도 센서를 만들 필요는 없습니다. 하지만 이렇게 말할 수는 있어야 합니다.

> "냉장고 온도가 5도보다 높으면 알려주세요."  
> "유통기한 지난 재료가 있으면 사용하지 마세요."  
> "손님에게 나가기 전에 주문 내용과 음식이 맞는지 확인하세요."

이게 검증 기준입니다.

AI 업무에서도 똑같습니다.

> "매출 total이 어드민 export와 다르면 멈춰주세요."  
> "원본 파일은 수정하지 마세요."  
> "Slack 발송은 자동으로 하지 말고 draft로 남겨주세요."  
> "원문 링크가 없는 평판 요약은 사용하지 마세요."

이런 문장이 나중에 hook이나 skill의 재료가 됩니다.

## Explain Hook

Hook은 쉽게 말하면 **자동 문지기**입니다.

어떤 일이 일어나기 전이나 후에 자동으로 확인하는 규칙입니다.

예를 들어 이런 상황을 생각해봅시다.

```text
리포트를 만들기 전
-> 데이터 기간이 맞는지 확인

리포트를 만든 직후
-> row count와 total 확인

외부로 보내기 전
-> 사람이 승인했는지 확인

자동화가 실패했을 때
-> 실패 로그를 남기고 사람에게 알림
```

이런 것이 hook의 생각 방식입니다.

하지만 비개발자에게 "hook을 만들어보세요"라고 말하면 어렵습니다. 대신 이렇게 질문하세요.

> "언제 자동으로 확인해야 하나요?"  
> "무엇이 틀리면 멈춰야 하나요?"  
> "멈췄을 때 누구에게 알려야 하나요?"

이 질문에 답하면 hook의 설계 재료가 나옵니다.

## Explain Skill

Skill은 쉽게 말하면 **반복 작업 설명서**입니다.

한 번만 하는 일이 아니라, 계속 반복되는 일이 있을 때 그 순서를 고정해두는 것입니다.

예를 들어 매주 매출 리포트를 만든다고 해봅시다.

매번 이렇게 말하면 번거롭습니다.

> "이번 주 매출 데이터를 가져오고, 환불을 제외하고, 지난주와 비교하고, 어드민 export와 total을 맞춰보고, 이상하면 알려줘."

이 일이 반복된다면 skill 후보가 됩니다.

비개발자는 skill 파일을 직접 만들 필요는 없습니다. 대신 이렇게 정리하면 됩니다.

```text
이름: 주간 매출 리포트 검증
언제 쓰나요: 매주 월요일 리포트 만들 때
필요한 데이터: 결제 데이터, 환불 데이터, 어드민 export
해야 할 일: 매출 계산, 환불 반영, 전주 비교
검증: total 비교, sample row 확인
하면 안 되는 일: 자동 발송, DB 수정
실패 시: draft로 보류하고 확인 질문 생성
```

이 정도만 써도 에이전트나 개발자는 skill로 바꿀 수 있습니다.

## Four-step Teaching Method

수업에서는 네 단계로 가르치면 됩니다.

### Step 1. Checklist

먼저 체크리스트부터 만듭니다.

비개발자가 가장 쉽게 할 수 있는 수준입니다.

예:

- [ ] 데이터 기간이 맞는가?
- [ ] row count를 확인했는가?
- [ ] 매출 total이 원본과 맞는가?
- [ ] 원본 파일을 수정하지 않았는가?
- [ ] 발송 전 승인을 받았는가?

여기서 중요한 것은 완벽한 자동화가 아닙니다.  
먼저 "무엇을 확인해야 하는지"를 눈에 보이게 만드는 것입니다.

### Step 2. Verification Prompt

두 번째는 검증 문장을 프롬프트 끝에 붙입니다.

예:

```text
검증:
- 사용한 데이터 source와 기간을 먼저 적어주세요.
- row count와 total을 원본과 비교해주세요.
- 숫자가 맞지 않으면 분석을 중단하고 확인 질문을 해주세요.
- 이메일/Slack 발송은 하지 말고 draft로만 남겨주세요.
```

이 단계부터 에이전트가 검증 기준을 따라 움직이기 시작합니다.

### Step 3. Reusable Verification Template

세 번째는 반복되는 업무에 템플릿을 만듭니다.

예:

```text
검증 이름: 주간 매출 리포트 검증

언제:
- 리포트 생성 직후
- 공유 전

확인할 것:
- 매출 total이 어드민 export와 맞는가
- 환불이 기준대로 처리됐는가
- 기간이 월요일~일요일인가
- 테스트 결제가 제외됐는가

실패 기준:
- total 차이가 1% 이상이면 중단
- 환불 기준이 불명확하면 중단
- 수신자에게 자동 발송 금지

실패 시:
- 확인 질문 생성
- draft 상태로 보류
- 검증 실패 항목을 표로 남김
```

이 템플릿은 아직 코드가 아닙니다. 하지만 자동화로 바꾸기에 충분히 구체적인 업무 규칙입니다.

### Step 4. Skill Or Hook Candidate

네 번째 단계에서야 skill이나 hook 후보로 표시합니다.

비개발자는 이렇게만 적으면 됩니다.

```text
이 검증은 매주 반복됩니다.
자동화 전 항상 실행되어야 합니다.
실패하면 자동 발송하지 말고 멈춰야 합니다.
```

이 문장이 있으면 에이전트나 개발자가 다음으로 바꿀 수 있습니다.

- checklist
- prompt block
- reusable skill
- pre-run hook
- post-run hook
- approval gate
- automation failure handler

## Classroom Dialogue

튜터:

> 여러분, hook이나 skill을 직접 만들 필요는 없습니다.  
> 여러분은 "무엇을 매번 확인해야 하는지"만 정하면 됩니다.

학생:

> 그럼 제가 코딩을 몰라도 자동화 검증을 만들 수 있나요?

튜터:

> 네. 코딩은 몰라도 됩니다. 대신 이런 말을 할 수 있어야 합니다.  
> "이 숫자는 어드민 export와 맞아야 합니다."  
> "다르면 멈춰야 합니다."  
> "외부 발송은 사람이 승인해야 합니다."

학생:

> 그게 hook인가요?

튜터:

> 그 문장을 자동으로 실행되게 만들면 hook이 됩니다.  
> 여러분이 쓰는 것은 hook 코드가 아니라 hook의 규칙입니다.

학생:

> skill은요?

튜터:

> skill은 반복 작업 설명서입니다.  
> 매주 같은 방식으로 리포트를 만들고 검증한다면, 그 순서를 skill 후보로 정리할 수 있습니다.

## Tutor Prompt

수업 중 에이전트에게 이렇게 시킬 수 있습니다.

```text
아래 비개발자 검증 규칙을 보고 checklist, prompt block, skill 후보, hook 후보로 나눠주세요.

규칙:
- 매출 total은 어드민 export와 비교해야 합니다.
- total 차이가 1% 이상이면 중단해야 합니다.
- 환불 기준이 불명확하면 사람에게 질문해야 합니다.
- 이메일 발송은 자동으로 하지 말고 draft로 남겨야 합니다.

출력:
- 비개발자용 체크리스트
- 프롬프트에 붙일 검증 블록
- 반복 skill 후보
- hook 후보
- 사람이 승인해야 할 action
```

## Closing

마지막으로 학생에게 이렇게 정리합니다.

> hook이나 skill을 만들려고 하지 마세요.  
> 먼저 자동화가 실행되기 전에 반드시 확인해야 할 조건과, 실패했을 때 멈추는 기준을 적으세요.  
> 그 기준이 반복되면 에이전트가 checklist, prompt, skill, hook으로 바꿀 수 있습니다.

핵심 문장은 이것입니다.

```text
비개발자의 역할은 구현이 아니라 기준 정의다.
검증 기준이 명확해야 좋은 자동화가 가능하다.
```
